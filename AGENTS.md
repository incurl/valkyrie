# AGENTS.md

Repository instructions for AI coding agents. Keep this file short, concrete, and tied to commands that actually work in this
repo. If a fact here conflicts with source files or CI config, trust the source file and update this guide.

## Project Snapshot

Valkyrie is a **scaffold**: a desktop application template built on Wails v3, an embedded PocketBase and a React frontend. It
is not a product. The plumbing every application needs is done; the domain is yours to write.

- Backend: Go 1.26 (toolchain `go1.26.10` pinned in `go.mod`), Wails v3.0.0, PocketBase v0.39.11. The binary is `main.go` at
  the repo root (no `cmd/`).
- Frontend: React 19, TypeScript, Vite 8, TanStack Query v5. Three runtime dependencies only (`react`, `react-dom`,
  `@tanstack/react-query`) plus `@wailsio/runtime`. No UI kit, no CSS framework, no i18n.
- Persistence: PocketBase owns the database (SQLite). It runs **as a library**, never as a process. Collections are defined in
  `internal/pocketbase/migrations/*.go` and registered through a blank import in `internal/pocketbase/service.go`.
- Generated API outputs: `frontend/bindings/` for TypeScript. It is generated by `wails3 generate bindings` and is **gitignored**.
  Never hand-edit it, never commit it.
- Module path: `github.com/incurl/valkyrie`.

## The One Concept That Matters

**The job queue is generic; the runner is yours.**

`internal/jobs` models a job as a title, a prompt, an arbitrary `map[string]any` of params and an arbitrary result. It owns
the lifecycle only: persistence, bounded concurrency, cancellation, status transitions, and the Wails event push.

The work is delegated to a `jobs.Runner`:

```go
type Runner interface {
    Run(ctx context.Context, job Job) (*Result, error)
}
```

`internal/runner/echo.go` is a working reference implementation that echoes the prompt back, so the scaffold runs out of the
box with no external service. **Replacing it is the first thing an application does.** The README shows exactly how.

`internal/runner/example.go` is a second, **compiled and tested** reference: it shows the three things every runner must do —
read the credentials in Go, honour the context, and return a `*jobs.Error` when a numeric code is wanted. Copy it rather than
writing a runner from scratch, so the API cannot drift under you.

Everything else — the queue, the storage, the cancellation, the events, the history — keeps working no matter what the runner
does. Do not special-case a domain into `internal/jobs`.

## Architecture

```
Wails webview
├── React 19 + Vite + TanStack Query
│   ├── app/           the shell: layout, data fetching, the event wiring
│   ├── features/      one panel per concern (submit, queue, console, settings)
│   ├── bindings/      typed wrappers over the generated bindings
│   └── ui/            pure helpers (zoom), unit tested
│
└──── Wails bindings (primary channel) ───────────────────────┐
        Go: internal/bindings/ → internal/jobs/ → internal/runner/
                                                (your backend) │
                            └→ internal/pocketbase/            │
                                    (embedded, library)       │
                                     └→ migrations, file fields│
        PocketBase's REST + file API mounted at /api/* on the    │
        same origin as the UI.                                   │
```

## Working Rules

- Read relevant code before editing; prefer local patterns over new abstractions.
- Keep diffs scoped. Do not do repo-wide cleanup, dependency churn, or generated-file rewrites unless the task requires it.
- **The frontend never talks to PocketBase or a remote API directly.** Every call goes through `internal/bindings` and the
  typed wrappers in `frontend/src/bindings/index.ts`. If a component needs new backend behaviour, add a method to
  `AppService`, regenerate the bindings, and add a wrapper.
- **Never hand-edit `frontend/bindings/`.** It is generated and gitignored. Change the Go service, then run
  `wails3 task common:generate:bindings`.
- **Never hand-edit `frontend/dist/`.** It is the `//go:embed` payload, built by Vite and gitignored.
- New collections and fields go in `internal/pocketbase/migrations/` as a Go migration registered in an `init()`. The file
  name is the migration's identity *and* its ordering key: the list is sorted by name, so a new migration must be named with a
  timestamp that sorts after the ones already applied (`1730000000_init.go` → `1732000000_add_x.go`).
- PocketBase's collection access rules are the write gate. The scaffold ships read-only public rules (`ListRule`/`ViewRule`
  set to `""`) on `jobs` and `artifacts`, and **no** rule at all on `app_settings`, so the Go backend is the only reader of
  the secrets. Do not open `app_settings` to the frontend.
- Secrets are write-only from the UI's point of view. The API key is encrypted with AES-256-GCM before it is written, and the
  key lives in a `0600` file in the data directory. The UI only ever learns *whether* a key is present. Never return a secret
  from a bound method.
- The debug console shows a **fingerprint** of a secret, never the secret itself (`console.Fingerprint`).
- Ask before adding heavy dependencies, changing auth/token behaviour, or altering the Docker/release workflows.

## Commands

Run from the repository root unless a command starts with `cd`.

**`wails3` is not on the default PATH of non-interactive shells.** It lives in `~/go/bin`. The `task` binary is *not* needed
either — `wails3 task` runs the Taskfiles itself. Prefix the command:

```bash
PATH="$HOME/go/bin:$PATH" wails3 build
PATH="$HOME/go/bin:$PATH" wails3 task common:generate:bindings
```

```bash
# Backend
go test ./...                                  # all Go tests (the build/ios package always fails to build; ignore it)
go test -race ./internal/... .                # the race detector, as CI runs it
go vet ./internal/... .
gofmt -l internal/ main.go main_test.go tools/ # must print nothing
go run ./tools/e2e-check                       # a live end-to-end run of the backend

# Frontend (from frontend/)
npm install
npm test                                       # vitest
npm run typecheck                              # tsc --noEmit, includes the test files
npm run build                                  # tsc && vite build -> frontend/dist

# Bindings
PATH="$HOME/go/bin:$PATH" wails3 generate bindings -clean=true -ts -i   # same as common:generate:bindings

# Builds
PATH="$HOME/go/bin:$PATH" wails3 build          # -> bin/valkyrie
PATH="$HOME/go/bin:$PATH" wails3 task build:server   # -> bin/valkyrie-server
PATH="$HOME/go/bin:$PATH" wails3 task package        # the platform packages
PATH="$HOME/go/bin:$PATH" wails3 task --list-all     # every task, with names

# Audits
python3 tools/license-audit.py                 # fails on a copyleft dependency
```

### Task names are namespaced

The Taskfiles are `include`d under `common:`, `linux:`, `windows:`, `darwin:`, `ios:` and `android:`. The bare names in the
root `Taskfile.yml` (`build`, `package`, `run`, `dev`) work, but the tasks defined in `build/Taskfile.yml` are only reachable
through their namespace: `common:generate:bindings`, `common:generate:icons`, `common:install:frontend:deps`.

**`wails3 task --summary <name>` executes the task; it does not describe it.** To list, use `wails3 task --list` (described
tasks) or `wails3 task --list-all` (everything). To inspect without running, use `wails3 task --dry <name>`.

## Change Routing

| Change | Update | Verify |
| --- | --- | --- |
| A backend method the UI calls | `internal/bindings/service.go`, then regenerate the bindings, then a wrapper in `frontend/src/bindings/index.ts` | `go test ./internal/... .` and `npm run typecheck` |
| The job lifecycle (queue, cancellation, status) | `internal/jobs/` | `go test -race ./internal/jobs/...` |
| The application's actual work | `internal/runner/` and its registration in `main.go` | `go test ./internal/runner/...` and `go run ./tools/e2e-check` |
| A collection or a field | `internal/pocketbase/migrations/` (a new file with a later timestamp) | `go test ./internal/pocketbase/...` |
| Settings or secrets | `internal/pocketbase/settings.go`, `internal/pocketbase/crypto.go` | `go test ./internal/pocketbase/...` |
| A panel or the layout | `frontend/src/features/`, `frontend/src/app/App.tsx`, `frontend/src/styles.css` | `npm run typecheck && npm test` |
| The product name, identifier or version | `build/config.yml`, `build/*/Taskfile.yml`, `internal/bindings/service.go` (`AppName`, `AppVersion`), `frontend/package.json`, `Taskfile.yml` (`APP_NAME`) | `wails3 build` |
| A dependency | `frontend/package.json` or `go.mod` | `python3 tools/license-audit.py` |

## Frontend Conventions

- One panel per concern under `frontend/src/features/`. Keep the pure logic (the helpers, the formatters) in a separate file
  next to the component and unit test it — the console panel and the queue are the reference: `ConsolePanel.tsx` exports
  `formatDetail`, `entryToText` and `writeClipboard` beside the component, and `ConsolePanel.test.ts` tests them.
- **Never import a generated binding file directly.** Use `frontend/src/bindings/index.ts`. It re-exports the generated
  modules behind a strongly typed surface and normalises the nullable arrays the generator produces (`artifact_ids: string[]`,
  `params: Record<string, unknown>`).
- The generated bindings type a missing array as nullable. The backend always sends an array, so the wrapper normalises it.
  Keep that normalisation at the wrapper, not in the components.
- The Wails event stream pushes job updates; the React Query `refetchInterval` is only the safety net. Do not raise the
  interval to "fix" a stale UI — check the event subscription in `frontend/src/app/App.tsx`.
- The stylesheet expresses every size in `rem`, because the zoom factor scales the root font size (`frontend/src/ui/zoom.ts`).
  A `px` size does not scale with the interface.
- `color-scheme: dark` is set on `:root`. Without it, WebKitGTK renders the native select popup with a light background while
  the option text stays light, which makes the selected item appear blank.

## The Webview Gotchas

These cost real debugging time in the source project. They are properties of the webview, not of this codebase.

- **`navigator.clipboard` needs a secure context and a user gesture**, which a webview does not always provide. The copy
  buttons fall back to a hidden textarea plus `document.execCommand('copy')`. A copy button that silently does nothing is
  this, not a missing handler.
- **A click that ends a text drag fires the row's click handler.** The console rows check `hasTextSelection()` before
  toggling the detail view, so that selecting a message and reading it stay out of each other's way.
- **`user-select: none` on a copy button** keeps the button's label out of the text the reader selects. Without it, "Copy"
  ends up inside the pasted text.
- The clipboard fallback must not use `display: none`, which makes the textarea unselectable and breaks the copy command.
  It is positioned off-screen with `opacity: 0` instead.

## Server Mode

The same binary runs headless with `-tags server`. It serves the frontend and the PocketBase API over HTTP, with no GUI
dependencies.

```bash
VALKYRIE_DATA_DIR=/tmp/valkyrie WAILS_SERVER_PORT=8080 ./bin/valkyrie-server
```

`WAILS_SERVER_HOST` overrides the bind address (default `localhost`; the container image sets `0.0.0.0`). `WAILS_SERVER_PORT`
overrides the port (default `8080`). The container image is `task build:docker`.

## Data

Everything lives in `pb_data/` next to the executable: `data.db` (SQLite), `storage/` (the files), and `.valkyrie_key` (the
AES-256-GCM key, mode `0600`). `VALKYRIE_DATA_DIR` relocates it — use that to run against an isolated database during
development and testing.

- Before finishing, run the checks that match the changed surface from "Change Routing".

## Known Rough Edges

1. **`go build ./...` fails on `build/ios`** with `function main is undeclared in the main package`. This is expected: it is a
   separate `main` package behind the `//go:build ios` tag. Build the root package and `./internal/...` instead.
2. **npm 9.2.0 cannot resolve the vitest 4 peer tree** and fails with `Cannot read properties of null (reading 'edgesOut')`. Use
   `npm install --legacy-peer-deps`, or a newer npm. This is a bug in the old npm, not in the dependency set.
3. **The `.npmrc` sets `minimum-release-age`**, which pnpm and bun honour but npm ignores. It is a forward-looking guard, not
   an active protection under npm.
4. **`build/Taskfile.yml` pins the frontend install to `npm install`** in the `common:` namespace, while the root
   `Taskfile.yml` exposes a `PACKAGE_MANAGER` variable. The per-manager tasks exist; the default is npm.
